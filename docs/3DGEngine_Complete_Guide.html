Part I — Foundations

How the codebase is organised, how the editor drives it, and the three pillars every system builds on: the ECS, scenes, and assets.

1. Architecture & the four targets

3DGEngine is a from-scratch C++17 engine on OpenGL 3.3 with a Dear ImGui editor. The code is split into four targets with a strict dependency boundary:

TargetRoleDepends on
engineReusable runtime library — ECS, rendering, physics, animation, audio, AI, assets.—
gameYour project's gameplay scripts (native C++), registered into the engine's ScriptRegistry.engine
editorAuthoring: scene editing, asset import, the material/animation/particle editors, and Play mode.engine, game
playerThe standalone runtime (RuntimePlayerApp) that loads an exported scene with no editor code.engine, game

The golden rule: the runtime never depends on the editor. Anything a shipped game needs must live in engine or game. The editor authors data; the runtime consumes exported data.

The runtime frame

Each frame runs a variable-rate update, zero or more fixed updates, then render:

Window events
  → variable Update      input, scripts (OnUpdate), audio, animation, camera, UI
  → N fixed updates       game mode, scripts (OnFixedUpdate), gameplay, AI,
                          controllers, ragdoll, physics step, contact events
  → Render                shadows → PBR/static/skinned → sky/water → particles
                          → post-process → HUD → editor overlays
  → swap buffers
Rule of thumb Put anything that affects collision or must be frame-rate independent in OnFixedUpdate. Put presentation (reading input for UI, camera feel, cosmetic effects) in OnUpdate. Gameplay time is globally scalable (slow-mo, hit-stop); editor UI and audio mixing stay on unscaled time.

2. The editor at a glance

The editor is a dockable ImGui workspace. The panels you will use most:

Viewport

Scene view with gizmos. Select, move, rotate, scale objects; frame the camera; enter Play.

Hierarchy

The scene's object list. Multi-select, lock selection, group move/delete.

Inspector

Per-object components. Add components one at a time via + Add Component; each has its own header with a Remove button.

Content Browser

Your project's assets. Import, organise, and drag assets into the scene. Files dropped from Explorer open an Import dialog.

Asset editors

Material Maker, Clip Editor, Graph Editor, Character Editor, Particle Editor, Shader Editor, Behavior Graph, HUD editor.

Console / Profiler

Log output (import results, script build status, warnings) and a frame-time graph.

A project owns a Content root, a scene, and its scripts. File → New Project creates one; each project's scripts are isolated (see §10). The editor autosaves and remembers the last opened project and scene.

3. ECS: entities, components, systems

Everything in a scene is an entity (an id) with components (plain data) held in an engine::ecs::Registry. Systems are free functions that iterate components.

Core components

ComponentPurpose
Transformposition (vec3), rotation (quat), scale (vec3). Model() builds the matrix.
RuntimeNameThe object's name — how scripts and saves find entities across a reload.
MeshPBR / MeshRendererDrawable mesh + PBR material / renderer flags.
Collider, RigidBodyPhysics shape and body (§9).
LightDirectional / point / spot light.
ModelAsset, MaterialAsset, SkinnedModelAssetAsset references the runtime resolves into GPU/runtime objects.
AnimatedModelA rigged model + its controller + computed pose (§8).
NativeScriptComponentAttaches one or more scripts to an entity (§10).

Typical iteration inside a system or script:

registry.view<Transform, Health>().each(
    [&](ecs::Entity e, Transform& t, Health& h) {
        if (!h.alive) t.position.y -= 0.1f;   // sink dead things
    });
Why names matter Entity ids are not stable across a scene reload or a save/load. When you need to refer to a specific object later (a script target, a save slot), match by RuntimeName. Script::FindObject("Door") does exactly this.

4. Scenes, prefabs, worlds & level streaming

There are two scene formats: the editor scene you edit, and the runtime scene the editor exports for Play mode and the standalone player. Authoring lives in the editor scene; the runtime consumes the exported one.

  • Prefabs (.3dgprefab) — reusable object templates. Place many, edit the prefab, instances update.
  • Worlds (WorldManifest) — a set of levels with placement offsets, the basis for streaming.
  • Level streaming — the LevelStreamingManager loads/unloads levels at runtime. Scripts request it with RequestLevelLoad("Level2") / RequestLevelUnload(...). Streaming runs in packaged worlds (the editor Play preview is a single in-memory scene).

Scene transitions from a script use RequestSceneLoad("NextLevel"); the host loads the target scene and continues play.

5. Assets: import, registry, cooking

Assets flow from a source file to an engine-owned native asset with a stable id:

Source (FBX/OBJ/glTF/PNG/JPEG/WAV…)
  → editor Import (with settings)
  → native asset (.3dgmesh/.3dgskmesh/.3dgskel/.3dganim/.3dgtex) + stable AssetHandle
  → AssetRegistry (.3dgdb)
  → scenes/materials/characters reference the ID (path is a readable fallback)
  → RuntimeAssetManager resolves & caches GPU/runtime objects at load
  → AssetCooker copies only what an exported scene actually reaches

Importing

Use the Content Browser's Import button, or drag files from Explorer onto the window. A drop opens an Import Settings dialog that scans each file's type:

  • Models are peeked for a skeleton — a rig auto-selects Skeletal Mesh (or Animation Only when there is no mesh), otherwise Static Mesh. Each row shows a summary (e.g. skeleton, 1 mesh, 6 anim) and lets you override the mode.
  • Textures get sRGB and Smooth toggles; sRGB defaults off for normal/roughness/metal/mask/AO maps (detected by filename).
IDs over paths Once imported, assets are referenced by a stable GUID. You can move or rename assets in Content and references still resolve. Paths remain as human-readable fallbacks.

6. Rendering, lighting & cameras

The renderer is physically based (PbrRenderer) with a separate skinned path (SkinnedRenderer) for characters, plus sky, water, terrain, particles, and a post-process pass. You rarely call it directly — you place drawable entities and lights and the frame loop renders them.

Making something visible

  • Give an entity a Transform and a mesh (a MeshPBR with a material, a ModelAsset, or a SkinnedModelAsset).
  • Add at least one Light (a directional "sun" is the usual key light) and set the environment (sky / IBL) for ambient.

What the renderer already optimises

  • Frustum culling and mesh LODs (distance-based) are automatic.
  • Backface culling is on for closed solids; flat planes and transparent (glass) materials render two-sided.
  • Cascaded / point / spot shadows; untextured meshes are instanced into one draw.

Cameras

In Play, the camera is usually driven by the PlayerController view mode (Third Person / First Person / Isometric / Platformer) or by a Camera Zone trigger that blends to an authored camera preset. Scripts can shake the camera and play camera sequences (cutscenes) via the scripting API (§10).

Editor tip The Material Maker's preview draws two-sided so you can inspect back faces; scene rendering keeps backface culling for performance.

7. Materials, textures & shader graphs

A material (.3dgmat) is authored in the Material Maker with a live PBR preview. It exposes the standard PBR inputs plus advanced lobes:

InputMeaning
Albedo / mapBase colour (sRGB texture).
Metallic, Roughness / mapSurface response; often packed in one texture.
Normal map, strengthSurface detail (linear texture).
EmissiveAdditive glow (flash on an event from a script).
Clearcoat, Transmission, Sheen, Subsurface, AnisotropyAdvanced BRDF lobes for car paint, glass, cloth, skin, brushed metal.
UV scale / offset / rotationTexture placement.

Shader graphs (.3dgshader) let you build custom materials in the Shader Editor; the same graph compiler powers both the Material Maker preview and scene rendering, so the preview is faithful.

Using a material

Assign a .3dgmat to an object's material slot in the Inspector, or drag it onto the object. From a script you can tint/flash via the animated model's material fields.

Texture import Remember to import color maps as sRGB and data maps (normal/roughness/metal/AO) as linear — the drag-drop Import dialog pre-selects this from the filename, but confirm it.

8. Skeletal animation, graphs & characters

Animation is layered as three authored asset types feeding a runtime controller:

  1. Clip (.3dgclip) — one source FBX/native take + strip-root-motion / loop / speed. Authored in the Clip Editor (with a live skinned preview).
  2. Graph (.3dggraph) — a state machine built from clips: states, parameters, transitions, and 1D/2D blend spaces. Authored in the Graph Editor.
  3. Character (.3dgcharacter) — rig + collider + controller + a reference to a graph, plus sockets/attachments. Authored in the Character Editor.

The controller & blend spaces

At runtime a graph becomes an AnimationController with states, parameters (Float / Bool / Trigger), transitions, and blend spaces. The play loop drives parameters each frame — Speed, Direction, IsMoving, IsGrounded, IsFalling, and more — so a locomotion blend space picks the right pose automatically.

Transition traps A transition on a Float parameter defaults matter: Speed >= 0 is always true and will skip a state on frame 1. Give numeric transitions a real threshold (e.g. Speed > 0.1), and use == for Bool/Trigger. The Graph Editor's Validation strip flags always-true transitions, unresolved clip names, and unreachable/dead-end states — fix the red/yellow items before testing.

Root motion

A state's Root Motion flag transfers the clip's root translation and yaw to the character, so turning and curved-locomotion clips steer the entity while the mesh stays centered. Straight clips are unaffected.

Foot IK (opt-in)

Enable Foot IK in the Character Editor to ground feet on slopes and steps at runtime. It raycasts the scene, plants each foot with a two-bone solve, and drops the pelvis so both legs reach. Leg bones auto-detect from common rig names (Mixamo/UE/generic). Tune trace distance, foot height, pelvis strength, and IK weight per character.

Driving animation from a script

void OnUpdate(float dt) override {
    Anim().SetParameter("Speed", currentSpeed);
    Anim().SetBool("IsGrounded", grounded);
    if (WasKeyPressed(GLFW_KEY_F))   // an attack
        Anim().PlayAction("Attack");          // one-shot over locomotion
}

9. Physics, colliders, queries & ragdolls

The PhysicsWorld is an impulse solver with a spatial-hash broadphase. You give entities colliders (and optionally rigid bodies); the fixed step integrates and resolves them.

Components

  • Collider — shape (Sphere/Box/Capsule/Cylinder/Cone/Pyramid/Torus/Staircase/Plane), material (restitution, friction), collision layer/mask, and a trigger flag (overlap-only, never blocks).
  • RigidBody — mass (inverse mass; 0 = static), gravity, sleeping, CCD, freeze rotation, kinematic (moved by script/animation, pushes others, never pushed).
  • Physics Setup presets in the Inspector: Dynamic Body, Static Collider, Trigger.

Queries

engine::Ray ray{ origin, glm::vec3(0,-1,0) };
engine::RaycastHit hit = physics.Raycast(registry, ray, /*maxDist*/50.f,
                                         /*layerMask*/0xFFFFFFFF, /*ignore*/self);
if (hit.hit) { /* hit.entity, hit.point, hit.normal, hit.distance */ }

SphereCast is available for volume queries (camera booms, thick probes).

Triggers & events

Mark a collider as a trigger to get overlap events instead of blocking. In a script:

if (WasTriggerEntered(FindObject("Checkpoint")))
    SaveCheckpoint("cp1", Transform()->position);

Joints & ragdolls

Distance / rope / spring joints connect bodies. A character with a Ragdoll (enabled on Health, activate-on-death) replaces animation with connected physics bodies at zero HP — tune mass, body count, thickness, damping, and death impulse.

10. Gameplay framework & the scripting API

Gameplay logic lives in scripts. A native script is a C++ class deriving from engine::Script; you attach it to an object via the Inspector's + Add Script. The editor generates the registration and (after a script rebuild) the script runs in Play and in packaged builds. Lua is planned as a second, no-rebuild backend behind the same interface.

Per-project script isolation

Each project owns its script list, stored next to its .project file. Opening or creating a project regenerates the shared game module's script header from only that project's scripts — so a new project starts with none and never inherits another project's classes. Create scripts with the Inspector or the Behavior Graph's template tools.

Script lifecycle

MethodWhen
OnCreate()Once, when the object enters Play / is spawned.
OnUpdate(dt)Once per rendered frame (variable dt) — input, camera, cosmetics.
OnFixedUpdate(dt)Per physics step (fixed dt) — movement, forces, anything touching collision.
OnDestroy()Before the entity/script is removed.

What a script can reach

The Script base exposes a large, grouped API. Highlights:

  • Self & world — Self(), Registry(), Transform(), FindObject(name), FindTransform(name), TryGet<T>()/Has<T>()/Add<T>(), SpawnFromObject(prototype, pos), DestroySelf().
  • Input — Input().KeyDown(k)/KeyPressed(k), mouse buttons and deltas.
  • Timers & sequences — SetTimer(sec, fn, repeat), Delay(sec, fn), Sequence().Do(...).Wait(2).Do(...).
  • Time control — SetGlobalTimeDilation(), HitStop(seconds).
  • Animation — Anim().SetParameter/SetBool/SetTrigger, PlayAction(name), PlayActionClip(name).
  • Audio / Particles / Camera — Audio().Play(), Particles().Burst(), Camera().Shake(), Camera().PlaySequence(name).
  • Triggers & events — WasTriggerEntered/Exited(e), WasAnimationEvent(name).
  • Fields — inspector-exposed GetFieldFloat/Int/Bool/Vec3/Entity/Asset so designers tune a script without recompiling.
  • Persistence — SaveInt/Float/Bool/Vec3 & GetSaved…, checkpoints, and full save slots (§15).
  • Flow — RequestSceneLoad(path), RequestLevelLoad/Unload(level), and Game() for the shared GameMode (score/state).

A complete script

#include <engine/gameplay/Script.h>

class Coin final : public engine::Script {
public:
    void OnCreate() override {
        m_spin = GetFieldFloat("spinSpeed", 90.0f);   // designer-tunable field
    }
    void OnUpdate(float dt) override {
        if (auto* t = Transform())
            t->rotation = glm::rotate(t->rotation, glm::radians(m_spin*dt),
                                      glm::vec3(0,1,0));
    }
    void OnFixedUpdate(float) override {
        if (WasTriggerEntered(FindObject("Player"))) {
            Game()->AddScore(1);
            Audio().PlayCue("Content/SFX/coin.wav");
            DestroySelf();
        }
    }
private:
    float m_spin = 90.0f;
};

11. AI & navigation

Agents combine a Nav Agent component, a navmesh/grid for pathing, and either a hand state machine (AiAgent) or a Behavior Graph (.btgraph) with tasks/decorators/services. Perception is vision (a cone + a line-of-sight raycast) and hearing (a decaying sound field: footsteps scale with speed, combat noise on HP loss).

Authoring an agent

  • Add a Nav Agent to a character: speed, force, reach radius, repath interval, vision range/angle, hearing range, team, and either a named Chase Target or Auto-target (nearest enemy of a different non-zero team).
  • Bake a navmesh over the level (editor Navigation preview), or use a nav grid.
  • Give it a Behavior Graph, or rely on the built-in Patrol → Chase → Search states, which react to sightings and heard noises; squads share alerts and flank shared targets.
Scale note Auto-targeting snapshots candidate targets once per frame, so many agents stay cheap. For hundreds of agents, back it with the physics spatial hash.

12. Audio

The AudioEngine (miniaudio) mixes up to 64 voices with priority-based voice stealing and per-bus groups (SFX / Music / Dialogue…). Attach an authored sound to an object, or fire cues from scripts.

  • Spatial sources — a component with attenuation (min/max distance, rolloff), Doppler, cones, occlusion, looping, and a bus. Play/pause/seek from a script: Audio().Play(), Audio().SetVolume(v), Audio().Stop().
  • One-shot cues — Audio().PlayCue("path.wav", spatial).
  • Adaptive music — Audio().LoadMusic(path) + Audio().SetMusicState("combat") (beat-synchronised), plus mixer snapshots and dialogue ducking.

13. Particles

Particle systems are authored in the Particle Editor (modules: emission, shape, velocity, color/size over life, forces) and attached to objects. Scripts control them via Particles(): Play(), Stop(clear), Burst(count), SetRate(perSec), SetSpeed(sim), Count(). Use presets to start, then tune curves. Great for pickups, impacts, weather, and magic.

14. UI & HUD

A HUD (.hud) is a document of widgets authored in the HUD editor and drawn each frame by the text/UI renderer. Widgets bind to runtime values by name:

  • Health bars/text bound to the player's Health.
  • Named floats/strings — score, time, gamestate, gamemessage from GameMode, plus any you push from a script via the HUD context.
  • Buttons with actions (e.g. Restart, Exit) for pause/end screens.

The standalone player draws the scene's HUD plus a status overlay and the in-game save/load menu (§15).

15. Save/Load system

The engine's SaveGame module captures world state into numbered slots with metadata (name, source scene, timestamp) and restores it after a scene reload. Entities are matched by RuntimeName (ids aren't stable across a load).

  • Captured — per named entity: Transform, Health, linear/angular velocity — plus the flat key/value store scripts write.
  • Script API — typed values SaveInt/Float/Bool/Vec3 + GetSaved…; full slots SaveGameToSlot(n, name) / LoadGameFromSlot(n); and checkpoints SaveCheckpoint/LoadCheckpoint.
  • In-game menu — the packaged player quick-saves with F5 and opens a slot menu with F9 (Up/Down select, Enter load, Del erase). A load reloads the saved scene and restores the snapshot.
// autosave at a checkpoint trigger, then continue-from-save on death
if (WasTriggerEntered(FindObject("Checkpoint"))) SaveGameToSlot(0, "Checkpoint");
if (!Game() /*player died*/ ) LoadGameFromSlot(0);

Part III — Build a Game

A start-to-finish walkthrough that assembles the systems into a small playable game: a third-person character collects coins in a level while an enemy hunts them, with a HUD, audio, checkpoints, and a packaged build. Follow it in order; each step names the system it uses.

16. Project setup & importing assets

  1. New Project — File → New Project, pick a folder and name. This creates a Content root and an empty, isolated script set (§10).
  2. Import assets — drag your files from Explorer onto the window. In the Import dialog: confirm the character FBX imports as Skeletal Mesh, props as Static Mesh, color textures as sRGB and normal/roughness as linear (§5).
  3. Make a material — open the Material Maker, set albedo/roughness/normal, save a .3dgmat (§7).

17. Building the level & the player

  1. Floor & props — drop a plane and some meshes into the viewport, assign materials. Give the floor a Static Collider and props colliders as needed (§9).
  2. Light & sky — add a directional Light as the sun and set the environment for ambient/IBL (§6).
  3. Animate the character — in the Clip Editor wrap idle/walk/run takes into .3dgclips; in the Graph Editor build a 1D locomotion blend space driven by Speed (use Create 1D Locomotion); resolve any Validation warnings; save a .3dggraph. In the Character Editor reference that graph, set the capsule collider, and enable a Player Controller (Third Person). Optionally enable Foot IK (§8).
  4. Place the player — add the character to the scene, name it Player, and add a PlayerStart so the runtime binds the camera + controller.
  5. Test — press Play. Walk around; the blend space should move idle→walk→run as speed rises (drag the Character Editor's Speed slider to preview outside Play).

18. Scripting the gameplay loop

Create a Coin script (Inspector → + Add Script) using the class from §10: it spins, and on the player entering its trigger it scores, plays a cue, and destroys itself. Place several coins (make one a prefab and stamp copies). Add a GameRules script on an empty object to end the game when the score reaches the coin count:

void OnUpdate(float) override {
    if (Game()->Score() >= GetFieldInt("coinsToWin", 5))
        Game()->Win();     // GameMode victory -> HUD end screen
}

Rebuild scripts (the editor prompts / the Script Editor triggers the build), then Play.

19. Enemies, AI & combat

  1. Bake navigation — open the Navigation preview and bake a navmesh over the floor (§11).
  2. Add an enemy — place another character, give it a Nav Agent (team 2, auto-target on, vision + hearing ranges), and a name. It will chase the player when it sees or hears them, search the last-known spot, then return to patrol.
  3. Combat — give the player and enemy Health. On an attack input, play an attack action and, on the animation's hit event, damage whatever the player's forward raycast hits:
void OnUpdate(float) override {
    if (Input().KeyPressed(GLFW_KEY_SPACE)) Anim().PlayAction("Attack");
    if (WasAnimationEvent("hit")) {
        engine::Ray r{ Transform()->position + up, forward };
        auto h = /* physics.Raycast via a system, or a trigger on the weapon */;
        if (auto* hp = TryGet<engine::Health>(h.entity)) hp->Damage(25.f);
    }
}

A dead enemy with a Ragdoll (activate-on-death) collapses into physics bodies (§9).

20. HUD, audio, saving & packaging

  1. HUD — author a .hud with a health bar bound to the player and a score text bound to GameMode; add an end-screen message bound to gamemessage (§14).
  2. Audio — attach ambient music (adaptive: calm ↔ combat), and cues for coins/hits. Set a Music bus and duck it under dialogue if any (§12).
  3. Checkpoints & saves — place trigger volumes that call SaveGameToSlot(0, "Checkpoint"); the player can also F5-save / F9-load in the packaged build (§15).
  4. Package — export the runtime scene and build the standalone player. The AssetCooker copies only assets the exported scene reaches. Ship the player executable + the cooked content.
Editor-Play parity Scene transitions (RequestSceneLoad) now work in editor Play as well as the packaged runtime, so you can test level flow without packaging first. Level streaming still runs only in packaged worlds.
You now have a level, an animated player with locomotion + optional foot IK, collectibles with scoring, a hunting enemy with perception and ragdoll, a HUD, audio, checkpoints/saves, and a shippable build — touching every major system.
